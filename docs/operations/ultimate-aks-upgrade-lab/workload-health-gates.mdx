# Step 4: Add a Workload Compatibility Health Gate

Steps 1 through 3 protected the platform. None of them can protect you from a problem only the application team can see: logic inside the workload itself that quietly assumes something about the Kubernetes version it's running on. A common real-world pattern is a certification or compliance check — someone writes code that says "only run if the cluster is on a Kubernetes version my team has already validated," ships it, and nobody remembers to update that check the next time the cluster gets upgraded. From AKS's point of view, nothing went wrong: the upgrade succeeded, the node drained cleanly, the pod rescheduled without incident. From the application's point of view, it just broke.

This step builds a minimal version of that failure, and the gate that would have caught it. The pattern is intentionally simple: the application declares, in a ConfigMap, the Kubernetes minor version its current build was certified against. A CI job compares that declaration to the cluster's *live* version before anything downstream — a deploy, a promotion, a Fleet approval — is allowed to treat the cluster as healthy. If the two disagree, the pipeline fails loudly instead of letting a silent mismatch ship. It's the workload-owned equivalent of how AKS already [blocks cluster upgrades when it detects deprecated Kubernetes API usage](https://learn.microsoft.com/azure/aks/stop-cluster-upgrade-api-breaking-changes) — except here you're encoding your own application's compatibility contract rather than relying on a Kubernetes-API-level check. See [AKS production upgrade strategies](https://learn.microsoft.com/azure/aks/aks-production-upgrade-strategies) for more on why workload-level guardrails like this one matter alongside platform-level ones.

## 4.1 Declare the workload's supported Kubernetes version

Deploy a ConfigMap holding the minor version this application was last certified against, alongside a small Deployment representing the application itself. In a real pipeline, `expectedK8sMinor` is something a developer updates deliberately as part of their own release process — the point of this exercise is to notice how easy it is to forget that step, and what happens when you do.

```bash
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: ConfigMap
metadata:
  name: version-locked-app-compat
  namespace: upgrade-lab
data:
  expectedK8sMinor: "33"
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: version-locked-app
  namespace: upgrade-lab
spec:
  replicas: 2
  selector:
    matchLabels:
      app: version-locked-app
  template:
    metadata:
      labels:
        app: version-locked-app
    spec:
      containers:
      - name: web
        image: nginx:1.25.5
        ports:
        - containerPort: 80
EOF
```

## 4.2 Add the comparison as an explicit CI gate

Add this job to the workflow from Step 2, running after the upgrade completes. Walk through what it actually checks before you run it: it reads the declared expected version out of the ConfigMap, reads the live server version straight from the cluster via `kubectl version`, and fails the job the moment the two disagree — before anything downstream is allowed to treat this cluster as healthy. It also confirms the Deployment has available replicas, because a version match on a crashed workload isn't actually a healthy workload.

```yaml
  workload-health-gate:
    runs-on: ubuntu-latest
    needs: precheck-and-upgrade
    steps:
      - name: Azure Login
        uses: Azure/login@v2
        with:
          creds: ${{ secrets.AZURE_CREDENTIALS }}

      - name: Validate workload compatibility gate
        uses: Azure/cli@v2
        with:
          inlineScript: |
            az aks get-credentials \
              --resource-group "${{ github.event.inputs.resourceGroup }}" \
              --name "${{ github.event.inputs.clusterName }}" \
              --overwrite-existing

            EXPECTED=$(kubectl get configmap version-locked-app-compat -n upgrade-lab -o jsonpath='{.data.expectedK8sMinor}')
            CURRENT=$(kubectl version -o json | jq -r '.serverVersion.minor' | tr -d '+')

            if [ "${EXPECTED}" != "${CURRENT}" ]; then
              echo "Health gate failed: expected minor ${EXPECTED}, found ${CURRENT}"
              exit 1
            fi

            AVAILABLE=$(kubectl get deploy version-locked-app -n upgrade-lab -o jsonpath='{.status.availableReplicas}')
            if [ -z "${AVAILABLE}" ] || [ "${AVAILABLE}" -lt 1 ]; then
              echo "Health gate failed: no available replicas."
              exit 1
            fi

            echo "Health gate passed."
```

Try it yourself: once Step 1's cluster has moved to a Kubernetes minor version newer than the `33` hardcoded in the ConfigMap above, run this job and watch it fail with a clear `Version mismatch` message instead of silently approving a broken state. That failure message is the whole point — it's the difference between an app team finding out from a dashboard versus finding out from a customer.
