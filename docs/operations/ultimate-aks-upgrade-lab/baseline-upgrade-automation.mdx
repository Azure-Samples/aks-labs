# Step 1: Baseline Upgrade Automation

AKS clusters that never get upgraded have a way of becoming a liability without anyone noticing. Once a cluster drifts far enough behind, it falls out of the [supported Kubernetes version window](https://learn.microsoft.com/azure/aks/supported-kubernetes-versions), loses official support, and accumulates unpatched CVEs in both the control plane and the node operating system. The instinct a lot of teams have, understandably, is to avoid automating upgrades altogether — an upgrade that fires at the wrong moment can disrupt production traffic just as easily as neglect can.

This step builds the piece that resolves that tension: automation you control. AKS exposes two independent auto-upgrade channels — one for the Kubernetes version, one for the node operating system image — and a planned maintenance system that lets you decide exactly when each of those channels is allowed to act. By the end of this step you'll have a cluster that upgrades itself, on a schedule you chose, not one AKS chose for you.

## 1.1 Set up your working environment

Before creating anything, set a few environment variables you'll reuse throughout the rest of this lab. `$RANDOM` keeps your resource names unique if you run this lab more than once in the same subscription.

```bash
RAND=$RANDOM
export LOCATION=eastus
export RG_NAME=rg-aks-upgrade-lab-$RAND
export AKS_NAME=aks-upgrade-lab-$RAND

az group create --name ${RG_NAME} --location ${LOCATION}
```

## 1.2 Create the cluster with both auto-upgrade channels enabled

This lab deliberately creates an **AKS Standard** cluster rather than AKS Automatic. AKS Automatic pre-configures upgrade defaults for you out of the box, which is great in production but skips past the decisions this lab wants you to make deliberately. Standard gives you the room to configure each of these settings yourself and see exactly what each one controls.

Two flags in the command below are doing the real work:

`--auto-upgrade-channel stable` subscribes the cluster to [Kubernetes version auto-upgrades](https://learn.microsoft.com/azure/aks/auto-upgrade-cluster), targeting the latest supported patch on minor version *N-1* — one minor version behind the newest release. That's a deliberate trade: you give up being on the absolute latest release in exchange for a version that's had more time to prove itself in the field. AKS also offers `patch` (same minor version only), `rapid` (always the newest minor version), and a legacy `node-image` channel, if your risk tolerance differs.

`--node-os-upgrade-channel NodeImage` is a separate decision, and it's easy to assume it's the same thing as the channel above — it isn't. [Node OS patches](https://learn.microsoft.com/azure/aks/auto-upgrade-node-os-image) (security fixes, kernel updates) ship on a much faster cadence than Kubernetes versions do, so AKS decouples the two lifecycles entirely. The `NodeImage` channel applies a fully AKS-tested image refresh on a weekly cadence; `SecurityPatch` is a faster, lighter-weight alternative that applies security-only fixes and can often avoid a full node reimage.

```bash
az aks create \
  --resource-group ${RG_NAME} \
  --name ${AKS_NAME} \
  --tier standard \
  --node-count 3 \
  --node-vm-size Standard_D2s_v3 \
  --generate-ssh-keys \
  --auto-upgrade-channel stable \
  --node-os-upgrade-channel NodeImage
```

> Some subscriptions restrict which VM SKUs you can deploy by default. If this command fails with a SKU allow-list error, change `--node-vm-size` to a size your subscription allows.

Connect `kubectl` to the new cluster so the rest of this lab can target it directly:

```bash
az aks get-credentials --resource-group ${RG_NAME} --name ${AKS_NAME} --overwrite-existing
kubectl config current-context
```

## 1.3 Decide when those upgrades are allowed to run

Turning on the two channels above only decided *that* upgrades will happen — it says nothing about *when*. That's the job of [planned maintenance](https://learn.microsoft.com/azure/aks/planned-maintenance), and it's arguably the more important of the two decisions: an upgrade channel with no maintenance window attached can, in theory, start at any time.

AKS supports three maintenance configurations, and they can all coexist on the same cluster because each one governs a different class of change:

- **`default`** governs AKS's own weekly platform releases — updates to control plane components and system add-ons that AKS ships on its own cadence, independent of your chosen upgrade channels.
- **`aksManagedAutoUpgradeSchedule`** governs the Kubernetes version channel you just configured.
- **`aksManagedNodeOSUpgradeSchedule`** governs the node OS channel.

We'll deliberately stagger these across the week — Sunday for AKS's own releases, Saturday for Kubernetes version bumps, Wednesday for node OS patches. There's nothing magic about these specific days; the point is that you decide when each class of change is allowed to land, and spreading them out means you're never stacking multiple kinds of disruption into the same window.

Default schedule, Sunday at 1am UTC:

```bash
az aks maintenanceconfiguration add \
  --resource-group ${RG_NAME} \
  --cluster-name ${AKS_NAME} \
  --name default \
  --weekday Sunday \
  --start-hour 1
```

Kubernetes version upgrades, Saturdays from 2–6am UTC:

```bash
az aks maintenanceconfiguration add \
  --resource-group ${RG_NAME} \
  --cluster-name ${AKS_NAME} \
  --name aksManagedAutoUpgradeSchedule \
  --schedule-type Weekly \
  --day-of-week Saturday \
  --interval-weeks 1 \
  --duration 4 \
  --utc-offset +00:00 \
  --start-time 02:00
```

Node OS image upgrades, Wednesdays from 2–6am UTC:

```bash
az aks maintenanceconfiguration add \
  --resource-group ${RG_NAME} \
  --cluster-name ${AKS_NAME} \
  --name aksManagedNodeOSUpgradeSchedule \
  --schedule-type Weekly \
  --day-of-week Wednesday \
  --interval-weeks 1 \
  --duration 4 \
  --utc-offset +00:00 \
  --start-time 02:00
```

Confirm both the channels and the windows actually took effect before moving on. `autoUpgradeProfile` should list both channels you set, and the maintenance configuration list should show all three windows:

```bash
az aks show \
  --resource-group ${RG_NAME} \
  --name ${AKS_NAME} \
  --query "autoUpgradeProfile" -o yaml

az aks maintenanceconfiguration list \
  --resource-group ${RG_NAME} \
  --cluster-name ${AKS_NAME} -o table
```

With this in place, the cluster will keep itself on a supported, patched Kubernetes version and node image automatically, but only during windows you've approved. The next step introduces a complication that automation alone can't solve: these upgrades are only as safe as the workloads running underneath them.
