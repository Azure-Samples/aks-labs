# Step 1: Baseline Upgrade Automation

:::info Why this matters
**The problem:** AKS clusters that never get upgraded silently drift out of the [Kubernetes support window](https://learn.microsoft.com/azure/aks/supported-kubernetes-versions), lose official support, and accumulate unpatched CVEs in both the control plane and the node OS. At the same time, teams are rightly cautious about turning on blind automation — an upgrade that kicks off at the wrong time can disrupt production traffic.

**How AKS solves it:** AKS Standard gives you two independent, opt-in auto-upgrade channels, plus a planned maintenance system that constrains *when* those channels are allowed to run. You get the security and support benefits of automation without losing control over timing.

- **[Cluster auto-upgrade channels](https://learn.microsoft.com/azure/aks/auto-upgrade-cluster)** keep the Kubernetes control plane and node version current. The `stable` channel targets the latest supported patch on minor version *N-1*, balancing new features against stability.
- **[Node OS auto-upgrade channels](https://learn.microsoft.com/azure/aks/auto-upgrade-node-os-image)** are a separate, faster-moving lifecycle for the node operating system image itself (security and kernel patches), decoupled from the Kubernetes version. The `NodeImage` channel applies a fully-tested weekly image refresh.
- **[Planned maintenance](https://learn.microsoft.com/azure/aks/planned-maintenance)** lets you control *when* those automated upgrades are allowed to execute. The `default` schedule governs AKS's own weekly platform releases, while `aksManagedAutoUpgradeSchedule` and `aksManagedNodeOSUpgradeSchedule` give you independent windows for the two auto-upgrade channels above — so you can, for example, patch node images midweek but only take Kubernetes version bumps on weekends.

Together, these three features are the foundation of a "set it and forget it" upgrade posture, and they're what every later step in this lab builds on.
:::

## 1.1 Create environment

```bash
RAND=$RANDOM
export LOCATION=eastus
export RG_NAME=rg-aks-upgrade-lab-$RAND
export AKS_NAME=aks-upgrade-lab-$RAND

az group create --name ${RG_NAME} --location ${LOCATION}
```

## 1.2 Create AKS cluster

```bash
az aks create \
  --resource-group ${RG_NAME} \
  --name ${AKS_NAME} \
  --tier standard \
  --node-count 3 \
  --node-vm-size Standard_D2s_v3 \
  --generate-ssh-keys \
  --auto-upgrade-channel stable \
  --node-os-upgrade-channel NodeImage
```

> **Note:** Some subscriptions restrict default SKUs. If the command fails with a SKU allow-list error, set `--node-vm-size` to an allowed SKU in your subscription.

Get credentials:

```bash
az aks get-credentials --resource-group ${RG_NAME} --name ${AKS_NAME} --overwrite-existing
kubectl config current-context
```

## 1.3 Configure planned maintenance

Shared/default schedule for AKS weekly releases:

```bash
az aks maintenanceconfiguration add \
  --resource-group ${RG_NAME} \
  --cluster-name ${AKS_NAME} \
  --name default \
  --weekday Sunday \
  --start-hour 1
```

Auto-upgrade schedule for Kubernetes upgrades:

```bash
az aks maintenanceconfiguration add \
  --resource-group ${RG_NAME} \
  --cluster-name ${AKS_NAME} \
  --name aksManagedAutoUpgradeSchedule \
  --schedule-type Weekly \
  --day-of-week Saturday \
  --interval-weeks 1 \
  --duration 4 \
  --utc-offset +00:00 \
  --start-time 02:00
```

Node OS schedule:

```bash
az aks maintenanceconfiguration add \
  --resource-group ${RG_NAME} \
  --cluster-name ${AKS_NAME} \
  --name aksManagedNodeOSUpgradeSchedule \
  --schedule-type Weekly \
  --day-of-week Wednesday \
  --interval-weeks 1 \
  --duration 4 \
  --utc-offset +00:00 \
  --start-time 02:00
```

Verify:

```bash
az aks show \
  --resource-group ${RG_NAME} \
  --name ${AKS_NAME} \
  --query "autoUpgradeProfile" -o yaml

az aks maintenanceconfiguration list \
  --resource-group ${RG_NAME} \
  --cluster-name ${AKS_NAME} -o table
```
