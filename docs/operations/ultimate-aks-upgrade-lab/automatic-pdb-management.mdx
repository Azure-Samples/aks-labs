# Step 3: Enable Automatic PDB Management

You just watched a single PDB block part of an upgrade. Now picture that same failure spread across dozens of teams and hundreds of deployments, most of whom have never thought about PDBs at all — either because they never set one, leaving their workload fully exposed to simultaneous eviction, or because they copied one from another team without fully understanding the implications. Asking every team to get this right, and to keep getting it right as replica counts and scaling behavior change over time, doesn't scale. This step fixes the problem at the platform layer instead of relying on every workload owner to fix it themselves.

[Automatic Pod Disruption Budget management](https://learn.microsoft.com/azure/aks/automatic-pod-disruption-budget-management) is an AKS cluster extension — not a change to any application. It watches the cluster for two situations and resolves both without anyone touching application code: Deployments with no PDB at all get one created automatically, sized to their current replica count; and when an existing PDB is actually blocking eviction during a drain, the extension temporarily adds just enough replicas to satisfy the budget, lets the drain proceed, then scales back down once it's done. It's still in preview, so treat what follows as something to evaluate rather than something to roll out everywhere unreviewed.

## 3.1 Install the extension

Install it scoped to the `upgrade-lab` namespace from Step 2, with automatic PDB creation turned on. The `controllerConfig.pdb.create=true` setting is what enables the proactive half of the extension's behavior — without it, the extension will still rescue you from an *existing* blocking PDB, but it won't create missing ones on your behalf.

```bash
az k8s-extension create \
  --cluster-name ${AKS_NAME} \
  --cluster-type managedClusters \
  --extension-type microsoft.evictionautoscaler \
  --name eviction-autoscaler \
  --resource-group ${RG_NAME} \
  --release-train stable \
  --configuration-settings controllerConfig.pdb.create=true controllerConfig.namespaces.actionedNamespaces="{upgrade-lab}" \
  --auto-upgrade-mode patch
```

> Do **not** include `kube-system` in `actionedNamespaces`. AKS already manages PDBs for its own system components, and the extension fails validation if an AKS-owned namespace is included in that list.

Confirm the extension finished installing before continuing — `provisioningState` should read `Succeeded`:

```bash
az k8s-extension show \
  --cluster-name ${AKS_NAME} \
  --cluster-type managedClusters \
  --name eviction-autoscaler \
  --resource-group ${RG_NAME} \
  --query "{state:provisioningState,version:currentVersion}" -o yaml
```

## 3.2 Watch it intervene

Rather than just taking the extension's word for it, force the exact situation it's designed to handle and watch the cluster respond. Find whichever node is currently running your `pdb-blocked-api` pods, cordon it, and drain it — the same operation an AKS upgrade performs on every node it touches.

```bash
NODE=$(kubectl get pods -n upgrade-lab -l app=pdb-blocked-api -o jsonpath='{.items[0].spec.nodeName}')
kubectl cordon ${NODE}
kubectl drain ${NODE} --ignore-daemonsets --delete-emptydir-data --force --timeout=300s
```

Without the extension running, this would be where you got stuck — `kubectl drain` would hang, or time out, against the same restrictive PDB from Step 2. Instead, look at what actually happened:

```bash
kubectl get pods -n upgrade-lab -l app=pdb-blocked-api -o wide
kubectl get pdb -n upgrade-lab
kubectl get evictionautoscalers -A
```

You should see a third `pdb-blocked-api` pod briefly scheduled onto a different node — the extension surging the replica count just enough to satisfy `minAvailable: 2` while the original pod on the cordoned node gets evicted — and an `EvictionAutoScaler` resource the extension created to track this PDB. Once the drain finishes, the extension scales the deployment back down to its original replica count on its own; no manual cleanup required.

Uncordon the node when you're done so the cluster returns to its normal schedulable state:

```bash
kubectl uncordon ${NODE}
```
