# Step 5: Drive the upgrade with Fleet

[Azure Kubernetes Fleet Manager](https://learn.microsoft.com/azure/kubernetes-fleet/) controls update sequencing across member clusters. We'll use it as the upgrade driver, without a GitHub repository, Actions workflow, or stored Azure credential secret. Allow 30-60 minutes plus maintenance-window waits.

The required exercise has one member and one stage so you can focus on the controls. It demonstrates the orchestration pattern, not a multi-cluster rollout. To extend it, add separately prepared disposable clusters to later groups and stages, link their shared maintenance windows, and assess each member before its stage starts.

## 5.1 Create a Fleet and join the lab cluster

A member's update group determines where it appears in the strategy. Joining Fleet doesn't copy workload policies or install the PDB Manager on other members; configure those independently.

```bash
export FLEET_NAME=fleet-upgrade-lab-$RAND
export RUN_NAME=run-k8s-upgrade-1

az fleet create \
  --resource-group ${RG_NAME} \
  --name ${FLEET_NAME} \
  --location ${LOCATION}

AKS_ID=$(az aks show --resource-group ${RG_NAME} --name ${AKS_NAME} --query id -o tsv)
az fleet member create \
  --resource-group ${RG_NAME} \
  --fleet-name ${FLEET_NAME} \
  --name ${AKS_NAME} \
  --member-cluster-id "${AKS_ID}" \
  --update-group group-a
```

## 5.2 Define separate preflight and post-upgrade approvals

Create `fleet-stages.json` with the following content. The before-stage approval is where you review Upgrade Insights. The after-stage approval is where you confirm the member and application are healthy after the upgrade. Neither approval runs checks itself.

```json
{
  "stages": [
    {
      "name": "stage-preprod",
      "beforeGates": [
        {
          "displayName": "upgrade-insights-reviewed",
          "type": "Approval"
        }
      ],
      "afterGates": [
        {
          "displayName": "workload-health-reviewed",
          "type": "Approval"
        }
      ],
      "groups": [
        {
          "name": "group-a"
        }
      ]
    }
  ]
}
```

```bash
az fleet updatestrategy create \
  --resource-group ${RG_NAME} \
  --fleet-name ${FLEET_NAME} \
  --name upgrade-strategy-lab \
  --stages fleet-stages.json

az fleet updaterun create \
  --resource-group ${RG_NAME} \
  --fleet-name ${FLEET_NAME} \
  --name ${RUN_NAME} \
  --upgrade-type Full \
  --kubernetes-version "${TARGET_VERSION}" \
  --node-image-selection Latest \
  --update-strategy-name upgrade-strategy-lab

az fleet updaterun start \
  --resource-group ${RG_NAME} \
  --fleet-name ${FLEET_NAME} \
  --name ${RUN_NAME}
```

Wait for `upgrade-insights-reviewed` to become `Pending`. Starting this run doesn't authorize its member upgrade until that approval is granted. Approvals require a stage-based strategy; they aren't supported in one-by-one update sequences.

## 5.3 Generate fresh Insights before approving

Fleet doesn't expose a documented built-in Upgrade Insights action. Use the same target as the run and review all scopes. Because this run also selects the latest node image, include a node-image assessment of each pool.

```bash
az aks upgrade-insights create \
  --resource-group ${RG_NAME} --name ${AKS_NAME} \
  --upgrade-type ControlPlaneAndAgentPools \
  --target-kubernetes-ver "${TARGET_VERSION}"

az aks nodepool list --resource-group ${RG_NAME} --cluster-name ${AKS_NAME} -o table
```

For each pool listed, run the following; omitting the target node image asks Insights to assess the latest available image:

```bash
read -r -p "Node pool name to assess: " POOL_NAME
az aks nodepool upgrade-insights create \
  --resource-group ${RG_NAME} --cluster-name ${AKS_NAME} \
  --name "${POOL_NAME}" --upgrade-type NodeImage
```

Don't approve if any required scope is failed, incomplete, or not evaluated. If a PDB finding persists, return to Step 3 rather than assuming installation of its manager clears static readiness checks. Generate new results after remediation. An assessment is a snapshot: cluster changes or a newer selected image can invalidate it.

Read gates from **this update run**, not the first pending gate returned across the whole Fleet:

```bash
az fleet updaterun show \
  --resource-group ${RG_NAME} --fleet-name ${FLEET_NAME} --name ${RUN_NAME} \
  -o json | jq '.status.stages[] | (.beforeGates // []) + (.afterGates // []) | .[]'
```

Find the `Pending` before-stage gate whose display name is `upgrade-insights-reviewed`. Copy the last component of its `gateId`, after the final slash. Open Step 4's health-request watch terminal **before** approving:

```bash
read -r -p "This run's pending preflight approval gate name: " GATE_NAME
az fleet gate approve \
  --resource-group ${RG_NAME} --fleet-name ${FLEET_NAME} --name "${GATE_NAME}"
```

This manual checkpoint avoids CI setup while making the decision visible in Fleet. For unattended operation, [Event Grid can notify an Azure Function, Logic App, or webhook](https://learn.microsoft.com/azure/kubernetes-fleet/howto-configure-events-for-gates). That integration would need to call Insights, wait for complete results, evaluate them, and approve only the matching run gate. It isn't a native preflight capability and isn't required here.

## 5.4 Observe maintenance and node health gates

```bash
az fleet updaterun show \
  --resource-group ${RG_NAME} --fleet-name ${FLEET_NAME} --name ${RUN_NAME} \
  -o json | jq '.status'
```

[Fleet honors member maintenance windows](https://learn.microsoft.com/azure/kubernetes-fleet/concepts-update-orchestration#planned-maintenance-windows), including the effective schedules linked through Step 1's shared windows. A member can wait outside its applicable window even after approval. Inspect the reported reason and schedule rather than bypassing the window to make the lab advance.

When the upgrade runs, answer each current node-scoped `HealthCheckRequest` using Step 4's smoke tests and response example. The Fleet approval doesn't replace those responses. If a health signal is unhealthy or times out, inspect both the member failure and the Kubernetes gate resources; don't approve the post-upgrade gate as a workaround.

For future multi-cluster exercises, automate the node-level provider before scaling out. Manually responding within five minutes on many clusters isn't a workable operational model.

## 5.5 Review the result and approve completion

Wait until the member update succeeds and `workload-health-reviewed` becomes `Pending`. Inspect node versions and workload health again:

```bash
kubectl get nodes -o wide
kubectl rollout status deployment/pdb-blocked-api -n upgrade-lab --timeout=180s
kubectl get deployment,pods,pdb -n upgrade-lab -o wide

az fleet updaterun show \
  --resource-group ${RG_NAME} --fleet-name ${FLEET_NAME} --name ${RUN_NAME} \
  -o json | jq '.status.stages[] | (.beforeGates // []) + (.afterGates // []) | .[]'
```

Repeat the HTTP smoke test from Step 4. Only after these checks pass, copy the exact pending after-stage gate's identifier and approve it:

```bash
read -r -p "This run's pending workload-health approval gate name: " GATE_NAME
az fleet gate approve \
  --resource-group ${RG_NAME} --fleet-name ${FLEET_NAME} --name "${GATE_NAME}"

az fleet updaterun show \
  --resource-group ${RG_NAME} --fleet-name ${FLEET_NAME} --name ${RUN_NAME} \
  -o json | jq '.status'
```

Confirm the run completed successfully. With additional stages, completion of one stage allows later stages to begin, subject to their own approvals and maintenance windows.

## Cleanup

If retaining the cluster, remove the manual health-provider policy after all upgrades finish so a future unattended upgrade doesn't wait for a person who isn't watching:

```bash
kubectl delete upgradegatepolicy lab-workload-health
```

Otherwise delete only the dedicated resource group created for this exercise. It contains the Fleet, member cluster, and shared maintenance resources; deleting it removes everything in that group and stops the associated charges:

```bash
az group delete --name ${RG_NAME} --yes --no-wait
```

## What you've learned

Shared maintenance controls upgrade timing, Insights identifies preflight blockers, the PDB Manager can preserve availability during drains, AKS health gates react during node upgrades, and Fleet sequences the rollout. These are complementary controls, not interchangeable checks. You exercised the flow without GitHub Actions.
