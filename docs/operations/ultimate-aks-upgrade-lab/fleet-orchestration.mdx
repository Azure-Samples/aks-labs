# Step 5: Fleet Orchestration

Up to this point, everything in this lab has operated on one cluster. That's a reasonable place to stop if you only run one cluster — but most organizations don't. Spin up a handful of clusters across regions, business units, or environments, and the problem stops being "did this upgrade succeed" and becomes "did it succeed everywhere, in the right order, without anyone babysitting twenty separate `az aks upgrade` commands." [Azure Kubernetes Fleet Manager](https://learn.microsoft.com/azure/kubernetes-fleet/) exists to answer that question.

Fleet's model maps cleanly onto ideas you've already used in this lab. A cluster joins a Fleet as a *member*. Members are organized into *groups* — by region, environment, or whatever makes sense for your organization. An *update strategy* defines the order those groups upgrade in, as a series of *stages*. The part that matters most for this lab is that a stage can have an *approval gate* attached to it, meaning the rollout literally stops and waits until something — a person, or a pipeline like the one you built in Step 4 — explicitly says it's safe to continue.

One detail worth calling out before you start: joining Fleet does **not** override the planned maintenance windows you set in Step 1. Fleet controls sequencing and approval *across* clusters; each cluster's own maintenance window still controls the *timing* of when it personally is allowed to be touched. If you kick off an update run outside a member's maintenance window, that member simply sits in a `Pending` state with a message telling you when its next window opens — you'll see this for yourself in 5.3.

## 5.1 Join your cluster to a Fleet

Create the Fleet resource, then join the AKS cluster you've been using as a Fleet member, placing it in an update group named `group-a`. Groups are how you'd eventually control which clusters move together in a real multi-cluster environment — with a single cluster, the group mostly exists so the strategy in the next step has something concrete to target.

```bash
export FLEET_NAME=fleet-upgrade-lab-$RAND

az fleet create \
  --resource-group ${RG_NAME} \
  --name ${FLEET_NAME} \
  --location ${LOCATION}

AKS_ID=$(az aks show --resource-group ${RG_NAME} --name ${AKS_NAME} --query id -o tsv)

az fleet member create \
  --resource-group ${RG_NAME} \
  --fleet-name ${FLEET_NAME} \
  --name ${AKS_NAME} \
  --member-cluster-id ${AKS_ID} \
  --update-group group-a
```

## 5.2 Define an update strategy with an approval gate

An update strategy is a reusable template, so you're not hand-writing the rollout sequence every time you upgrade. The one below is intentionally minimal — a single stage containing the one group you just created — but notice the `afterGates` entry of type `Approval`. That single field is what turns this from "Fleet blindly upgrades everything in order" into "Fleet upgrades this group, then waits for an explicit signal before considering the stage complete." In 5.4 you'll wire that signal to the same health check you built in Step 4.

Create `fleet-stages.json`:

```json
{
  "stages": [
    {
      "name": "stage-preprod",
      "afterGates": [
        {
          "displayName": "workload-health-gate",
          "type": "Approval"
        }
      ],
      "groups": [
        {
          "name": "group-a"
        }
      ]
    }
  ]
}
```

```bash
az fleet updatestrategy create \
  --resource-group ${RG_NAME} \
  --fleet-name ${FLEET_NAME} \
  --name upgrade-strategy-lab \
  --stages fleet-stages.json
```

## 5.3 Create and start an update run, then read what it tells you

An update run is the actual execution of a strategy against real clusters, targeting a specific Kubernetes version. Create one referencing the strategy above, then start it:

```bash
export TARGET_VERSION=<supported-target-version>

az fleet updaterun create \
  --resource-group ${RG_NAME} \
  --fleet-name ${FLEET_NAME} \
  --name run-k8s-upgrade-1 \
  --upgrade-type Full \
  --kubernetes-version ${TARGET_VERSION} \
  --node-image-selection Latest \
  --update-strategy-name upgrade-strategy-lab

az fleet updaterun start \
  --resource-group ${RG_NAME} \
  --fleet-name ${FLEET_NAME} \
  --name run-k8s-upgrade-1
```

Don't just glance at this next output — read it. The `status` block tells you exactly where the run is and why:

```bash
az fleet updaterun show \
  --resource-group ${RG_NAME} \
  --fleet-name ${FLEET_NAME} \
  --name run-k8s-upgrade-1 -o json | jq '.status'
```

If your cluster's maintenance window from Step 1 isn't currently open, you'll see the member sitting in a `Pending` state with a message like `member maintenance window is unavailable for update. next window opens at: ...` — this is Fleet correctly deferring to the maintenance window you configured, not a bug. If the window is open, you'll instead see the stage progress toward its `afterGates` entry, where it will pause and wait.

## 5.4 Approve the gate only after your health check passes

This job is the other half of the pattern: it looks up whatever approval gate is currently pending on your Fleet and approves it. The important detail is the `needs: workload-health-gate` line — this job only runs because the health check from Step 4 succeeded first. If that upstream job fails, this one never runs, and the stage stays paused indefinitely rather than rolling forward onto a cluster you haven't actually verified is healthy.

```yaml
  approve-fleet-gate:
    runs-on: ubuntu-latest
    needs: workload-health-gate
    steps:
      - name: Azure Login
        uses: Azure/login@v2
        with:
          creds: ${{ secrets.AZURE_CREDENTIALS }}

      - name: Approve pending Fleet gate
        uses: Azure/cli@v2
        with:
          inlineScript: |
            GATE_ID=$(az fleet gate list \
              --resource-group "${{ vars.RG_NAME }}" \
              --fleet-name "${{ vars.FLEET_NAME }}" \
              --gate-type Approval \
              --state Pending \
              --query "[0].name" -o tsv)

            if [ -z "${GATE_ID}" ]; then
              echo "No pending approval gate found."
              exit 1
            fi

            az fleet gate approve \
              --resource-group "${{ vars.RG_NAME }}" \
              --fleet-name "${{ vars.FLEET_NAME }}" \
              --name "${GATE_ID}"
```

## Summary

Over the course of this lab, you layered five independent upgrade safeguards on top of each other:

1. **Platform automation** — Kubernetes and node OS auto-upgrade channels, controlled by planned maintenance.
2. **Visibility into a real failure mode** — a restrictive PDB blocking a node drain, driven through CI.
3. **Platform-level remediation** — automatic PDB management removing that failure mode entirely.
4. **Workload-level protection** — a compatibility health gate catching application version-coupling bugs platform safeguards can't see.
5. **Fleet-scale orchestration** — the same safe-upgrade model applied across many clusters, with staged rollout and approval gates.

Each layer solves a problem the one before it couldn't, and each is independently useful on its own — you don't need Fleet to benefit from automatic PDB management, and you don't need health gates to benefit from planned maintenance. Together, they form a complete picture of what a mature AKS upgrade strategy looks like in production.
